# 协程块

这是一个未完成的设计，不一定会出现在标准中。作者也不确定这个设计的价值，也没有想明白所有该有的细节。

## 前言

线程簇和线程块最大的不同就是它太重量级了，它携带大量的状态，创造和销毁都需要大量的时间。当然程序员可以创造一个线程簇把它的资源池化，通过软件模拟不断的执行碎片化的任务。这些碎片化的任务相比于线程簇本身更接近于线程块的特征。

池化宿主资源，让轻量级的任务寄生于宿主的行为在传统的CPU和GPU的模型中都很常见。寄生于硬件SM中的线程块，以及寄生于CPU线程的协程就是是它们的代表。区别之一在于，前者几乎是硬件调度的，后者也是编程模型的概念纯粹的工作在用户空间。

Vacuum模型中提出了协程块的概念。用于实现GPU中的线程块和CPU中的协程功能，它的名字也是CPU风格的协程和GPU风格的线程块的简单拼接。考虑到这两个东西都是轻量级的协作性调度的调度单元，在两可性的IPU上用一个概念统一它们并固化在伴随式微内核的软件接口中是非常自然的想法。

## 草案和梗概

它的设计有两种不同的方案。第一种是协程块需要专门的函数和过程以及专门的同步原语，这样的设计更容易，但是API繁杂，协程的功能更简单/简陋，线程能调用的接口协程不一定能合法的调用。并且如何实现GPU的线程块的功能也是一个难题。另一种方案是在伴随式微内核上达成真正的统一的调用。我们假定每一个协程在执行的时候必须寄生一个线程簇，每一个协程会用一个bit来标记自己面对阻塞式系统调用以及同步原语比如锁的行为，

- 深度寄生模式，线程模式。行为接近于传统的CPU上的线程，面对阻塞式调用，会让线程簇失去核心的占用进入睡眠，面对同步原语如果获得锁失败，则原地自旋等待一段时间后让核心簇进入睡眠。

- 浅寄生模式，协程模式。行为接近于传统的CPU上的协程，面对阻塞式调用，会让返回线程簇中的上级调用者，上级调用者让当前协程沉睡hi主存并且。面对同步原语获得锁失败，则几乎不自旋就返回上级调用者。

在这种设计下一个函数无论被普通线程调用还是被协程调用，其行为逻辑可以保持一致。同步操作（如锁、I/O）的语义不再依赖特定的协程运行时或非阻塞API，这能显著降低代码的维护成本和心智负担。开发者无需再为“是否在协程环境”而编写两套逻辑。但是它就不能参考传统的CPU上的协程模型了，需要作者独立创造一个真正的新的协程块模型了。

## 设计困难

协程块在设计目标上需要同时服务于，轻量级和重量级任务，IO任务和计算任务。它需要可以实现大部分线程块和协程能做到的东西。

- 在GPU上用户可以发射数以十亿级的线程块，每一个线程块在SM上执行结束后的新任务切换极快，并且在线程块未开始执行时这十亿线程块只占用非常少的资源。那么用户也应当同时发射这种量级的协程块，并且未发射的协程不占用资源。这些协程块的启动和终止应当有接近线程块的速度。我们可以设置一个东西叫做协程种子的东西，记录需要发射的协程块的（三维）数目（就像CUDA那样），PC，参数以及协程块设置。此外协程种子记录已经发射的协程块的数目。线程簇可以通过操作协程种子，在自身中显式创建一个协程，如果遇到阻塞和解卸，那么把次协程簇回退到主存的全局协程状态空间，如果没有遇到此类机制，则执行至协程结束。结束后留在原地的资源则更可能传递给下一个协程。换言之它应当允许一个协程块在执行的开头和结尾它的信息都不进入主存。

- 如果它的功能模型高于传统CPU上的协程而更接近于线程， 那么显然可以在一个线程之内形成协程的调用链。换言之可以在一个线程里面装载N个协程块，当前块返回后回到上一个块，每个块按入栈顺序解卸。

- 块的问题。CPU上传统协程当然不用考虑簇容量的问题，但是Vacuum上的协程块可能有更大的块容量。这给调度机制额外增加了许多麻烦，但是这种调度机制不一定会写入全局接口。

## 状态位


### 协程比特位

- 原生协程块， 是否是线程建立时自带的原生的协程块。

- 深浅寄生， 决定面对阻塞，睡眠等的行为。

- 线程终止， 决定线程终止后是脱离寄生还是被强杀。

- 线程睡眠， 线程簇本身失去核心资源的时候是脱离寄生还是伴随睡眠。在链式调用的时候危险的行为。加入连续解卸了N个寄生协程块，那么它们重入的时候会被作为一个整体加载进新的协程吗？

- 信息置零， 安全设置，当协程块终止和卸载时，它在主存状态空间和被寄生的线程簇的信息是否置零。

- 主存状态拷贝，是否拥有被主存中的协程信息表项所记录，或者是悬空寄生在线程簇（可许合法）。

### 作为调用者

协程块显然可以选择创建和调用另一些协程块。当它选择把另一些协程块加载在自身原生的线程簇上的时候。它可以选择自身的状态。

- 自由态，当被调用者解卸，通过接口直接返回调用者协程。调用者协程自由决定接下来干嘛，可以执行自身任务，也可以选择执行新的协程。

- 播种态，选择一个协程块种子，当它播种完毕后或者连续执行指定数目的协程块后，返回调用者协程。期间线程簇完全在硬件和伴随式微内核的协助下，高速的加载并且调用种子协程。换言之此时模拟线程块的行为。播种态的线程簇被终止和睡眠时播种态本身如何继续？

- 混合态， 不清楚是否需要。当一个协程不愿进入播种态，但是也不想进入自由态而是作为一个纯粹的协程服务器时，它可以在操作系统的建议下，选择连续执行一些数目的协程块后回到自由态。这些被执行的协程块则由操作系统来调度。程序员设置上界，操作系统一段时间后发现没有新的可执行的协程块后也可以主动返回自由态。

自由态在功能上是完备的，但是在性能上可能有更大的切换协程上下文的开销，所以需要混合态和播种态。


## 权衡：线程簇需要纯粹容器化吗？

在很多操作系统中，进程仅仅是持有虚拟资源，比如虚拟内存和文件的容器，而不是调度的基本单位。线程用作独立的调度单元。Vacuum则面对更进一步的权衡，线程簇是否应该，也不是用作一个调度的单元。单纯的把它作为一个持有IPU核心资源，比如运行时间和局部物理存储器的容器。协程才是基本的调度单元，并且持有被调度所需要的基本资源，比如寄存器和栈信息。

假如纯容器化了会如何？也许不纯容器话更好，把协程块和线程簇都作为调度单元，这样的话，可以允许一些协程直接寄生在线程中，而不在全局内存中保留任何自己的状态？这个特性时刚需，但是不知道纯容器化是否会限制这一点。也许纯容器化也可以做到这一点


## 额外优势


协程块本身正如传统CPU的协程一样，几乎可以由用户程序自行软件模拟来实现。但是将它提升到伴随式微内核的一部分有额外的收益。分别是切换速度以及简化编程难度。这两个优势需要结合它的实现方式理解。
- 首先就是协程的切换速度。CPU风格的IPU很可能配备了一些硬件，比如上下文换入换出缓存加速执行上下文的切换。协程上下文本身的切换也可以由硬件辅助执行，而非用户态软件模拟。这种依赖硬件的执行当然需要暴露软件的接口给上层，为了办证实现自由更换，软件跨架构可迁移，它的实现必须是透明的，只能把概念本身比如协程块，暴露给用户。在GPU风格的IPU中，也可能会有一些加速播种的硬件机制暴露给

- 在这种设计下一个函数无论被普通线程调用还是被协程调用，其行为逻辑可以保持一致。同步操作（如锁、I/O）的语义不再依赖特定的协程运行时或非阻塞API，这能显著降低代码的维护成本和心智负担。开发者无需再为“是否在协程环境”而编写两套逻辑。但是它就不能参考传统的CPU上的协程模型了，需要作者独立创造一个真正的新的协程块模型了。

- 使用者可以用各种协程的调用设置组合出不同风格的协程块，甚至不同与传统线程块和传统协程的东西。

## 硬件需求

作为双层次指令集系统，不规范协程调度的具体实现，但是协程中心的设计要求的底线是硬件有一套机制可以避免协程操作要求更高的特权级。是否有全局的播种加速器和局部的的上下文切换缓存则并不一定强制。
