# 文档

这是Vacuum指令集的文档。Vacuum项目中并没有任何具体的实现，这些实现指的是包括物理指令集，伴随式编译器和伴随式操作系统的任何规范和代码。本项目只有在虚拟指令集层次的接口和规范。某种意义上的一纸空文。与数学物理化学不同，本规范并不是不容置疑的上帝的造物，而是一个或是一些具体的个人实现的工程。所以说阅读它的手册并不一定最好的理解它的方式，手册仅仅作为一种类似字典和百科全书一样的东西，供需要的人查询。在这个文档中，记录了Vacuum项目中项目设计动机。记住了设计的动机，理解规范是自然的。

但是文档本身并不像手册那样高度的结构化，它的主题更分散。

# 机器字长

我们注意到Vacuum规范目前支持16,32，64位的机器。

机器字长大约可以是8，16，32，64等等2的幂。在写下文档的今日，64位的机器已经是所有先进数字电路的默认之选的了。那么Vacuum支持32位或者是16位的程序有没有好处呢？个人的想法是支持越低的机器字长受益越低。这是因为两个原因，首先：Vacuum大约是系统由于伴随式编译器和伴随式操作系统等缘故，它会有一些额外的开销，对于规模越小的电路支持这种开销的能力越弱;其次Vacuum带来的所有的潜在性能收益都是基于增强了软硬件协同配合的角度带来的，比如它可以让设计师删去硬件中为了兼容而做出的冗余。然而低机器字长往往意味着更小的程序规模。比如说16位机器和8位机器上运行的代码，它的规模很难很大。这样的话，开发和迁移的成本也会更低。硬件设计师不必为了软件的兼容性而妥协，Vacuum本身带来的底层硬件的灵活性优势就很小。因此16位就是Vacuum支持的下界。

那么为什么不支持的更长呢？在摩尔定律放缓的今天，64这一个数字看起来能用很久。64位大约可以寻址160亿GB的地址空间。现实中可能只用48位大约256TB就已经很多了。更长的机器字长目前没有性能上的好处，只是负担。虽然我们对更长的字长的机器的需求遥遥无期，但是为什么不预先规定一种机器字长比如128位放在规范里呢？这就是作者水平的局限了。作者在思考，下一个机器字长如果真的来了，可能不一定是128位的，也可能是96位的。虽然128位很方便，各种好处很多，但是直接将机器字长翻倍其实对硬件的规模和时序的额外压力也是有的。人类在将64位机器更新成128位的那个时刻可能会经历一次硬件性能的可观测下降，此时也许会有一些替代技术，比如96位这种中间数位或者是重拾了分段技术来扩容。作者没有水平预测未来一定会怎样，所以只能将未来的标准留白。等待未来不知道什么时候64位不够用的时候再补上新的规范。

一个64位的机器支持32位程序需要额外的硬件，对成本性能和开发难度都是负面影响（虽然多大不一定）。那么在虚拟指令层支持多个机器字长非常符合Vacuum的初衷。然而这一设计并不像想象的那么自然和简单。如果不在虚拟层规定机器字长，立刻就会引起一个很大的问题。我们没法知道一个复合数据类型的长度和内存分布。所以虚拟指令层本身就要支持复合数据类型。这个原因会Vacuum的抽线层级就会比传统的汇编语言要高级一些。它不能看作一个模糊了实现细节的传统汇编语言。

像机器字长这样的和硬件的实现高度相关的参数其实还是有一些的，比如SIMD的宽度。这样的参数对程序的行为和虚拟指令向物理指令编译的结果有相当的影响。我们在规范里面称之为关键机器字面值。Vacuum虚拟指令在向下编译和转化的时候关键机器字面值的赋值是一个很关键的过程。

# 端序

为什么要固定vacuum的端序？不固定端序难道不会使得物理指令集的设计更灵活，可设计出的硬件更丰富吗？虽然是这样没错，但是不同端序的硬件的性能差异极小，支持多种端序带来的性能提升可以不计。但是它会给软件侧带来沉重的易用性负担。任何设计端序的软件都需要额外的逻辑来确定硬件侧的端序。Vacuum追求对编程的易用性和通用性。—而端序不固定是软件开发的“隐形陷阱”：对普通开发者：端序是底层细节，多数开发者无需（也难以）理解其原理，若需手动处理端序，会显著增加编程门槛（如多媒体处理中，图像像素数据在不同端序硬件上显示错位，排查难度极高）；- 对编译器/运行时：固定端序可让编译器无需生成“端序适配代码”，运行时（如伴随式编译解释器）也无需额外处理端序转换，降低软件栈的现复杂度，间接提升程序运行效率。
